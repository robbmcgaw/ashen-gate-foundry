# Ashen Gate | Profession Ledger

Module ID `ashen-gate-profession-ledger` · Foundry V14 · dnd5e. Owns each character's profession progression (XP, level) and known recipes, stored on Actor flags. Open it from **Actors sidebar → Professions** (players when **GM Setup → Player Access** is on).

**Sidebar folders.** Journals file under **Ashen Gate / Professions** (GM Data) and **Ashen Gate / Backups** (Refresh snapshots); see docs/folder-convention.md.

## Tabs

- **Individual:** a character's crafting bench: professions with level and XP, materials, recipe items to **Learn**, and known recipes to **Craft**. If a craft needs a party member's materials, that character's owner gets an Allow/Decline popup (the GM's client coordinates; any decline cancels). Each profession card has a GM-only **GM: XP** section: **Award** or **Adjust** (add, subtract or set, with a reason), and the XP history.
- **Party:** all party members' materials and recipes, by player or by profession.
- **Recipe Catalog:** recipes in folders by profession. Players see only recipes the party has found or learned; the GM sees all, with drafts marked. The GM gets **Open General Manager** at the end of the toolbar and the visibility guide in the GM notice. General Manager is the import path; the older Ledger JSON import is in a closed **Advanced: import here, or use General Manager** section at the end of the tab.
- **Gathering** (0.34.0, no lead gatherer): the GM opens a gather on **Gather**: **Ad-hoc**, a **Location spot** or a **Node template**. The GM ticks the gathering professions that can roll, the tier(s) and the DC (a saved spot fills in its own), then **Start gather…**. Every party character who holds one of those professions can roll one check (from the popup or their own Gathering tab; the GM can roll for them or record a total), using that character's own check mapping for the profession. Characters without the profession are not offered a roll. **Reveal results** settles every drop at once from the existing rules: success gives a Common material, success by 5+ a Rare one instead (Common if there is none), and a success may also find an Exotic (the spot's Exotic candidates, or for an ad-hoc gather the Exotic materials of the chosen professions and tiers, at the GM Setup discovery chance). A saved spot draws from its own material tables; an ad-hoc gather draws from the imported Materials of the chosen professions and tiers. Each successful character gets a different material while the pool has more to give. A slot-machine reel of material icons then lands on each drop (**Skip animation**; a plain list with reduced motion). The result is decided before the reel starts and nothing is given until the GM presses **Give loot**. If the Ledger cannot pick a drop, a pop-up lists who rolled, who met the DC and what each may receive (Common / Rare / Exotic) with **Give…** (Add per material) for each. If nothing can be picked the row says why (nothing imported, draft only, duplicate, unreadable import). Draft materials: **Use draft materials anyway** (GM only); players never see unreleased materials in the reel. A finite spot is spent by a gather; a gather nobody passes exhausts any spot. Players can still use **Request gather** on a spot they can see; **Approve** opens the gather, **Decline** (optional reason) tells the player. The GM's Gathering tab has **Requests (n)**, **Gather** and **Gathering nodes**. Starting, rolling for others, revealing, giving, approving and declining are GM-only in the API; a player rolls only for a character they own. Chat card per rolling character, with the XP award slot.
- **Gathering nodes** (GM, 0.25.0; the third sub-tab of **Gathering**, after Requests and Gather): node templates with a permanent `NODE-*` id, activity, gathering profession(s), tier range, check skill/tool, DC and common/rare/exotic material tables. Create, edit (the editor opens in place of the list, with **All nodes** to go back), duplicate, delete, import and export them; **Copy Location nodes** copies the gathering nodes Locations already has (Locations is never changed; the originals are backed up). Stored in the GM-only Journal *Profession Ledger (GM Data)*. Schema: [`docs/gathering-nodes-schema.md`](../../docs/gathering-nodes-schema.md).
- **Assign** (GM): previews which profession features each party character qualifies for, then adds the missing ones. A character qualifies by proficiency in the profession's **Skill to Access** or **Tool to Access** (either one). Fishing uses Survival by default (access and gather check). A carried-items list (0.20.0) from older GM edits, the Profession catalog or a baseline file still counts, but has no UI since 0.22.0.
  Its **Signature perks** sub-tab (0.31.0) is the catch-up for signature perks: preview which player characters hold a Journeyman or Expert tier but lack that tier's perks, then grant them (see Signature perks below).
  Its **Starting recipes** sub-tab (0.30.0) previews, per player character, the recipes marked `starting: true` for the professions it has (Will grant / Already known / Not granted with the reason for a draft or unreleased recipe), then grants the selected ones as known recipes without a recipe item. Re-running grants nothing new; press it again after a character gains a profession.
  **Refresh…** (0.33.0, in the Professions sub-tab, one character at a time) re-runs Assign for a player character whose proficiencies changed: it previews **Will add / Will keep / Will remove / Can't tell, left alone**, saves a GM-only snapshot Journal, removes what the Ledger can show it granted, then adds what the character now qualifies for. See *Refresh* below.
- **GM Setup** (GM): sub-tabs **Party**, **Tools and checks**, **Gathering & crafting** (Exotic discovery, crafted items) and **Player Access**, all saved together with **Save Changes** (Cancel discards and stays). **Tools and checks**: one row per profession, crafting then gathering, with **Skill to Access**, **Tool to Access** and (gathering only) **Tool for Advantage**: `advantageTools` applies to gathering professions only and is ignored for crafting. Each cell is a multi-select (0.27.0): it shows every value in effect and where it comes from (Default, From content, From baseline file, Set by GM); click it to tick values, **Clear (None)** empties it, **Done** or Escape closes it. The first skill and tool to access are also the profession's checks (the craft tool when a recipe names none; the gather tool and skill). Content names that match no dnd5e tool show as *Not matched: …*. Gathering checks use the advantage tools in effect, including the imported content's. The Tool for Advantage cell also lists **carried gear** (`advantageItems`, 0.27.0): carrying a matching item (inventory name in any case, a core UUID, or the dnd5e identifier; quantity above 0) gives advantage. Built-in: Archaeology = Calligrapher's Supplies; Fishing = carrying Fishing Tackle. **Reset to default** puts a row back to the default (a legacy carried-items list is kept). Under **Baseline file**, **Import baseline file…** reads a crosswalk file, shows which rows change, and applies it on **Apply baseline**. **Export current table** downloads the table in the same shape; only lists you or a baseline file set are written as overrides (0.22.1), the rest is shown under `inEffect`, which import ignores. Layers, lowest first: built in < Profession catalog `access` < baseline file < GM edits (GM edits always win). A layer only sets the lists it gives: a list the content leaves out keeps the built-in one, and an explicit empty list means none (0.29.1). Catalog definitions are matched by their PROF id first, then by name (0.22.1); names are matched ignoring `[TAG]`-style tags, case and punctuation, with a few aliases (e.g. `Arcana` → Enchanting, `Skinning` → Hunting). File schema: [`docs/profession-crosswalk-schema.md`](../../docs/profession-crosswalk-schema.md).

XP is never automatic: the GM awards it from the Individual tab (**GM: XP**) or from the **Award XP** control on gather and craft chat cards (with **Undo award**). The `ashenGateLedger.xpOpportunity` hook fires for each card.

A *Professions* tab is added to the character sheet when Tidy5e Sheet is active.

## Where data is kept

The recipe and material catalog (`libraryData`) is a world setting, and so are other Ledger records. World settings are sent to every connected browser, so the windows and the API show players only what they may see, but a player who opens the browser console could read the raw catalog, including recipes not yet released. That is fine for this table; it is not a secret store.

## Relation to other modules

Independent: it opens without any other Ashen Gate module. General Manager imports recipes (`REC-*`), materials (`MAT-*`), professions (`PROF-*`) and crafted items (`ITEM-*`); a craft copies the recipe's `result_item_id` world Item. A recipe may set `tool` (dnd5e tool key, tool Item UUID or name) or `workstation`; otherwise it needs its profession's tool, and crafting rolls a tool check shown on the card. Gathering nodes come from Locations when it is active. Skill Trees reads but never changes profession progress; profession perk choices stay here.

## Public API

`game.modules.get('ashen-gate-profession-ledger').api`: `open`, `playerAccess` (`ag-player-access/1`), `getProfessions`, `getProfessionProgress`, `getKnownRecipes`, `inspectProfessionPerkChoices`, `learnRecipe`, `craft`, `completeActivity` (0.28.0), `meetsProficiency` (0.28.0), `professions` (0.28.0), `awardProfessionXP` / `adjustProfessionXP` / `getProfessionXPHistory` (GM), `gathering.{nodes, start, round, roll, resolve, reveal, give, giveByHand, cancel, request, requests, approve, decline}` (0.34.0: `start` opens a round and ignores `leadId`/`helperIds`; `professions`, `tiers`, `dc` choose who may roll) (all but nodes/request are GM-only; 0.25.0: `start({templateId, tier, allowDraft})`, `approve(id, {allowDraft})`), `gathering.templates.{list, get, check, create, update, duplicate, remove, references, resolve, playerView, preview, import, export, copyFromLocations}` (GM only, contract `ag-gathering-nodes/1`), `assign.{preview, apply}`, `grantStartingRecipes` (0.30.0), `refreshProfessions` (0.33.0, GM only), `signaturePerks.{preview, grant}` (0.31.0, GM only) and `crosswalk.{previewBaseline, applyBaseline, exportTable, baseline}` (GM only), and `embed.mount`.

### `grantStartingRecipes(options)` (0.30.0, GM only)

- `grantStartingRecipes({preview = true, actorIds = null, rowIds = null})` → Promise. **GM only**: any other user is refused in the data layer, as is an `actorIds` entry that is an NPC, a character without a player owner, or a Character Hub level backup. Without `actorIds`: Assign's characters (the Ledger party, else dnd5e's Primary Party), player-owned characters only.
- `preview` (the default) writes nothing and returns `{preview: true, actors: [{id, name, hasProfession}], rows, startingRecipes}`; each row is `{id, actorId, actorName, recipeId, recipeName, profession, professionKey, status, reason}` with `status` `'new'`, `'known'` or `'unreleased'` (`reason` says why: draft/proposed, GM-only, reveal-gated, or not player-visible). A recipe belongs to a character when its `profession_id` is a PROF-* the character holds, or names the same profession.
- `preview: false` adds the `'new'` rows (only those in `rowIds`, when given) to each character's `knownRecipes` flag, re-checked just before writing, and returns `{preview: false, granted: [{actorId, actorName, recipes: [{id, name, profession}]}], skipped}`. Never uses or needs a recipe Item, never removes or duplicates a known recipe, and a second call grants nothing. All or nothing: if one character can't be updated, the characters already updated are put back and it throws. Profession level does not block it. Separate from `learnRecipe`, whose rules are unchanged.

### `refreshProfessions(options)` (0.33.0, GM only)

- `refreshProfessions({actorId, preview = true, removeProgress = [], alsoRemove = [], alsoRemoveRecipes = [], confirmName = ''})`. **GM only**, enforced in the data layer; refuses NPCs, characters without a player owner and Character Hub level backups. One character at a time.
- `preview` (default) writes nothing and returns `{preview: true, actor, willAdd, willKeep, willRemove, cantTell, blocked, notes, needsTypedConfirmation, counts}`. Qualification is Assign's (proficiency in a profession's Skill or Tool to Access).
- **What counts as granted by the Ledger.** (1) A profession feature or signature perk Item with the flag `flags.ashen-gate-profession-ledger.grant` (written by Assign and the perk grant since 0.33.0); (2) a known recipe that is a `starting: true` recipe of a profession being removed, or is listed in the Actor flag `grantedRecipes` (written by the starting-recipe grant). Anything else is never removed. A profession feature with no `grant` flag is listed under `cantTell` with an `optIn` Item id; pass it in `alsoRemove` to remove it. **0.33.3:** every `cantTell` row now has an opt-in. Profession features and signature perks without a `grant` flag carry `optIn` (an Item id, pass it in `alsoRemove`); known recipes the catalog doesn't know, or whose `knownRecipes` entry is not a valid recipe id or not text at all, carry `optInRecipe` (pass it in `alsoRemoveRecipes`; the value `@non-text` stands for all non-text entries). Ticked rows are listed in `willRemove` with a reason starting "Ticked by you", marked `ticked: true` in `cantTell`, saved in the snapshot, and removed (a recipe entry is taken out of `knownRecipes` and `grantedRecipes`; a perk or feature Item is deleted). A ticked perk needs `confirmName`. Anything not ticked is left alone. In the window, **Select all that I can’t identify** ticks every row.
- **Progress rail.** A profession being removed that has XP, XP history, chosen perks, Items crafted by the Ledger, known recipes beyond its starting ones or signature perks is listed in `blocked` and kept, unless its key is in `removeProgress`. Removing progress also removes its row in `professionProgress`, its learned recipes and its Ledger-granted signature perks, and needs `confirmName` equal to the character's name.
- `preview: false` saves a snapshot Journal (GM only, role `refresh-snapshot`, holding the removed Items and the previous `knownRecipes`, `grantedRecipes` and `professionProgress` flags) and aborts before any change if that fails; then updates flags, deletes the Items, and runs the Assign add path. Returns `{preview: false, actor, removed, added, kept, snapshot, blocked, cantTell, notes}`. Running it again changes nothing.

### Signature perks (0.31.0)

A `ProfessionPerk` record may be a signature perk: `signature: true`, `tier: "journeyman" | "expert"`, `profession_id: "PROF-…"`, and `point_cost: 0`. General Manager imports it as a feat Item (folder `Ashen Gate/Professions/<Profession>/Signature Perks`); it costs nothing and is in no skill tree. The Ledger finds it the way it finds Profession Items: the world Item bound to that `PERK-*` source id, read from Manager's source definition.

- **Automatic grant.** On `ashenGateLedger.progressionChanged` (fired on the GM client that wrote the XP), for each tier the change crossed upward (Journeyman level 4, Expert level 7), every signature perk of that profession and tier the character doesn't already hold is added to the character as an Item. One chat note per character and profession lists the perks. Idempotent: ownership is checked inside a per-character queue just before writing. Perks are never removed; lowering XP only adds a line to the Adjust XP confirmation. If nothing grantable is imported for a reached tier, the GM is told once per profession and tier.
- `signaturePerks.preview({actorIds = null})` → `{actors: [{id, name, hasProfession}], rows, signaturePerks}`; each row is `{id, actorId, actorName, perkId, perkName, professionId, profession, tier, level, status, reason}` with `status` `'new'`, `'held'` or `'unreleased'`. Writes nothing. Lists, for each player character, the signature perks whose profession the character holds at a level that reaches the tier.
- `signaturePerks.grant({actorIds = null, rowIds = null})` → Promise of `{preview: false, granted: [{actorId, actorName, perks: [{id, name, profession, tier}]}], skipped, failed: [{actorId, actorName, error}]}`. Adds the `'new'` rows (only those in `rowIds`, when given), re-checked just before writing, and posts the chat notes. A character that can't be updated goes in `failed`; the others still get theirs.
- **GM only**, enforced in the data layer: any other user is refused, as is an `actorIds` entry that is an NPC, a character without a player owner, or a Character Hub level backup. Without `actorIds`: Assign's characters (the Ledger party, else dnd5e's Primary Party), player-owned characters only.

### Professions, activities and `meetsProficiency` (0.28.0)

- `professions()` → `[{name, key, id, category}]`: the 14 original professions, then **Artistry** (`PROF-ARTISTRY`, category `creative`), then any other profession imported with category `creative`. `category` is `'crafting'`, `'gathering'` or `'creative'`. An imported Profession record declares it with `profession_kind` (`crafting` | `gathering` | `creative`) or `category: "creative"`.
- A Recipe record with `kind: "activity"` is a creative activity: no ingredients and no `result_item_id` needed. `completeActivity(actor, recipeId, {confirm})` (Owner or GM; same known-recipe and tier rules as `craft`) rolls the check and posts a chat card whose XP award works like a craft card's (flag `kind: 'activity'`; the `xpOpportunity` hook also gets `effort`). Nothing is created or used up. An activity's `required_tools` and optional `access` lists (`toolProficienciesAnyOf`, `skillProficienciesAnyOf`) are alternatives offered as checks.
- **Station or tool (0.34.1).** A recipe needs one tool or one workstation. When a recipe has a `workstation`, the tools in its `access.toolProficienciesAnyOf` are check-only roll choices: no *Uses* chip, no missing-tool warning, no block. Without a workstation they stay required alternatives, as before.
- **Recipe card text (0.33.4).** A card shows each fact once. If a recipe's `description` starts with a sentence that only repeats its tier and effort ("X is an apprentice ... made through short effort.") that sentence is left out, and any part of the `description` that is the same as (or contains) the `effect_note` is shown once, under **Effect**; only distinct text stays as the italic summary. Records are never changed. In Party and Recipe Catalog the card body (Needs/Makes, tool or station, summary, effect) folds under a **Details** control; the badges and **Known by** stay visible. "(the GM decides at the table)" appears only on cards where a character can complete the activity.
- **Open skill tree… (0.33.4).** Every profession card the character holds has an *Open skill tree…* button that opens its tree through the Skill Trees API (`open({actorId, treeId})`). It is shown only when Skill Trees is enabled and has `open`; players can use it for characters they own, the GM for any, and the handler enforces that.
- `meetsProficiency(actorIdOrActor, {toolProficienciesAnyOf?, skillProficienciesAnyOf?})` → `{ok, matched}`: whether the character is proficient in any listed tool or skill, resolved like Tools and checks (tool names or dnd5e keys, the group `Any musical instrument`, skill names or ids). `matched` lists the entries that matched, as written; an empty list is met. **Permission:** GM, or anyone with Observer on the Actor (like `progression.level`); not tied to Player Access.

### Suggested activity XP, effect notes and recipe names (0.29.0)

- Completing an activity prefills the GM's XP award with `max(1, ceil(tier × effort / 2))` (tier Apprentice 1 … Master 5, missing/unknown = Apprentice; effort Short 1, Long 2, Extended 3, missing/unknown = Short), still editable. The XP flag and the `xpOpportunity` payload carry `suggested` and `suggestedBasis` (plain words). Craft and gathering XP are unchanged.
- A Recipe record may carry `effect_note` (or `effectNote`): plain text up to 400 characters (longer is cut, non-text ignored), the boon an activity can give, decided by the GM. Shown in the recipe detail and on the Complete activity chat card; normalized recipes have `effectNote`. Nothing is automated.
- A Profession record may carry `recipeLabel` (singular) and `recipeLabelPlural`, 1–30 characters each (otherwise ignored). Display only: types, `REC-*` ids, API names and saved data don't change. Order: GM Setup → Tools and checks → Recipe names, then the imported record, then draft built-in names (Alchemy Formula, Blacksmithing Blueprint, Artistry Composition, awaiting approval), then Recipe. A missing plural is made from the singular.
- `recipeLabel(professionNameOrId, {plural = false, capitalize = true})` → the word, e.g. `"Formulas"`; unknown professions give `"Recipe"`. No permission needed (feature-detect it).

### `getProfessions(actor)` (0.18.0)

Read-only list of every profession the character has, for partner modules such as Character Hub. Works without Skill Trees.

```js
game.modules.get('ashen-gate-profession-ledger').api.getProfessions(actor)
// → [{professionId: 'PROF-HERBALISM', name: 'Herbalism', level: 2, xp: 5, xpToNext: 8, maxLevel: 16,
//     tier: 'Apprentice', unspentPerkChoices: 1}, ...]   sorted by name
```

- One row per `PROF-*` Profession Item on the Actor. A profession with no XP yet is level 1, 0 XP. `xpToNext` is XP still needed for the next level, `null` at `maxLevel` (16). `unspentPerkChoices` is 0 until the Ledger has tracked XP for that profession.
- No professions → `[]`. Never returns XP history or chosen perk ids.
- **Permission:** the GM, or a user with **Owner** permission on the Actor. Anyone else gets `Error('Actor access denied')`. Players also get an error while the GM has turned off the Ledger's Player Access. Players never see GM-only or reveal-gated Profession Items (same rule as the Ledger window).

### `embed.mount(element, options)` (0.19.0)

Shows one character's **Individual** panel (professions with XP and perk choices, materials, recipes to learn, known recipes with Craft) inside another module's window, for example Character Hub's Ashen Gate → Professions. The Ledger draws it and handles its buttons through the same code as its own window and the Tidy5e tab.

```js
const api = game.modules.get('ashen-gate-profession-ledger')?.api;
if (api?.embed?.mount) {
  const view = api.embed.mount(element, {actorId: actor.id, mode: 'individual'});
  // later: view.refresh();  view.unmount();
}
```

- `element`: a DOM element the caller owns. The Ledger replaces its contents and adds the class `agl-embed`.
- `options.actorId`: the character to show. `options.mode`: `'individual'` (the only mode; `api.embed.modes` lists them). An unknown mode or a missing element throws.
- Returns `{unmount(), refresh()}`. It refreshes itself when the character's Items or flags change or Player Access changes, and unmounts itself if the element has left the page.
- **Permission:** the GM, or the Actor's **Owner** (same as `getProfessions`). Anyone else sees "Only <name>'s owner and the GM can see this." Players see "The GM has hidden the Profession Ledger." while Player Access is off. Every button is checked again when clicked (learning needs Owner; XP awards and adjustments stay GM-only). Players never see GM-only or reveal-gated records.
